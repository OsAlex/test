### Q3a. ФОИВ код — окончательный ответ

**`1262 = "030"` для ВСЕХ товарных групп ЧЗ.**

Обоснование:
- `030` — код **ФНС** как оператора маркировки.
- Другие коды (041 — Минпромторг, 048 — РАР, 049 — Росздравнадзор) — только для систем, **не относящихся** к ЧЗ (ЕГАИС, МДЛП).
- Методичка v17 — всегда `1262="030"`.

**Не нужно ждать ответа Атол по этому пункту.** Зафиксировать в SPEC как факт.

### Q3b. Формат даты 1263 — окончательный ответ

**`ДД.ММ.ГГГГ`.**

Обоснование:
- Приказ ФНС ЕД-7-20/662@, таблица реквизитов, тег 1263.
- PIOT §6.3: `"21.11.2023"` — именно ДД.ММ.ГГГГ.
- ISO (`YYYY-MM-DD`) используется в **других** полях API ГИС МТ (`expireDate`, `productionDate`), но **не в теге 1263**.

**В SPEC §1.5 заменить «уточнить формат» на «формат ДД.ММ.ГГГГ (приказ ФНС)».**

### 2.2. `marking_check_history` — остались проблемы 🔴

**В §2.2 SPEC:**
```sql
found BOOLEAN NULL,
verified BOOLEAN NULL,
sold BOOLEAN NULL,
is_blocked BOOLEAN NULL,
```

**Хорошо** — исправлено. **Но** всё ещё есть `item_id VARCHAR(36) NOT NULL`. **Проблема:** в офлайн-проверке (ЛМ ЧЗ) привязка к `item_id` может быть не всегда — если проверка была **асинхронной** или **повторной**. Нужно либо `NULL`, либо заполнять при финализации.

**Дополнительно:** в §2.2 нет полей `cis` (только `code`), `gtin`, `group_id`, `parent_cis`. Для офлайн-проверок это критично.

**Исправление:**
```sql
cis VARCHAR(255) NULL,        -- выделенный КИ (для табака ≠ code)
gtin VARCHAR(14) NULL,
group_id INT NULL,
parent_cis VARCHAR(255) NULL, -- для агрегатов
```

### 2.3. §2.1 `marking_sell_queue.status` — `skipped` всё ещё неоднозначен 🔴

**В §2.1 SPEC:**
> «`skipped` — чек отменён до фискализации, `/cis/sell` не нужен. Либо: чек фискализирован, но запись в ЛМ ЧЗ **не нужна** (товар не маркирован, или `is_marked=false`). Либо: чек фискализирован, но КИ уже в БД проданных (дубликат).»

**Проблема:** три разных случая в одном статусе. Это создаст баги при обработке.

**Правильно разделить:**
- `skipped` — чек фискализирован, но запись не нужна (товар не маркирован). Не создаём запись вообще.
- `duplicate` — КИ уже в БД проданных. Отдельный статус, алерт.
- `cancelled` — чек отменён до фискализации. Запись **не создаётся**.

**Или:** использовать `skip_reason ENUM('not_marked','duplicate','cancelled_pre_fiscal')`.

**Проблема:** «или» — это не SPEC. Нужно **решение**.

**В SPEC зафиксировать:** «Таблица `marking_return_queue` (см. §2.9 — новая).»
