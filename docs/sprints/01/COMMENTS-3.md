## Часть 1. Ответы на открытые вопросы (Q1–Q7)

### Q1. Дата запуска — 01.03.2026 или 01.04.2026?

**Рекомендация: закладываться на 01.03.2026 как рабочий дедлайн, с буфером до 01.04.2026.**

Обоснование:
- Если 01.03 — это дата, после которой продажа немаркированного товара уже является нарушением, то любой сдвиг на 01.04 — просрочка. Наоборот не работает: если 01.03 — «мягкая» дата, релиз раньше срока безвреден.
- По методичке v17 срок токена продлён до 01.10.2026 — значит, до этой даты вся система уже должна работать.
- Влияние на приоритизацию: если 01.03 — обязательно покрыть **аварийные ситуации (HTTP 203)** и **офлайн-режим ЛМ ЧЗ** до релиза. Если 01.04 — можно релизить только онлайн, офлайн вынести во второй спринт.

**Что делать:** запросить у заказчика **номер и дату нормативного акта**, вводящего обязательную маркировку для целевых товарных групп. Это снимет вопрос полностью.

### Q2. Тайм-зона — MSK-only или выбор из конфига?

**Рекомендация: MVP — MSK-only (`timeZone=2`), но заложить интерфейс `Cassa::getTimeZone()` для будущего расширения.**

Обоснование:
- Абсолютное большинство российского retail — MSK/МСК+. Если все кассы в одном регионе — конфиг не нужен.
- **Но:** `timeZone` влияет на возврат `smp`/`mrp` (товарные группы 3, 12, 16). Если хотя бы одна касса в Калининграде (UTC+1) — MSK-значения `mrp` могут не совпасть с реальной минимальной ценой, и проверка цены ниже МРЦ даст ложный результат.
- В ФФД-1.2/Атол `timeZone` — это **часовой пояс МЕСТА РАСЧЁТА**, а не офиса компании.

**Что делать:**
1. Получить у заказчика список регионов присутствия.
2. Если все в MSK — зафиксировать `2` в конфиге.
3. Если есть регионы — сделать `Cassa::getTimeZone()` (поле в таблице касс) со значением по умолчанию `2`.
4. В SPEC явно указать: **диапазон 1..11, дефолт 2, при отсутствии значения в кассе — фоллбэк на `config('marking.default_timezone')`**.

### Q3. Официальный JSON-пример Атол (тег 1260) — где взять и что там должно быть

**Где искать:**
1. **ДТО 10.10.8.24** — документация драйвера ККТ. Раздел «ФФД 1.2» → «Отраслевой реквизит предмета расчёта».
2. **`АТОЛ FAQ`** — есть публичные примеры чеков с маркировкой (`atol.ru/support`).
3. **Личный кабинет Атол** — раздел «Документация» → «Примеры заданий».
4. **Поддержка Атол** — запрос «пример JSON для чека продажи маркированного товара (ФФД 1.2) с тегом 1260».

**Что должно быть в примере (ожидаемо):**

Для Атол API v2 (порт 16732, `api/v2/requests`) структура `industryInfo` находится **на уровне позиции чека** (`items[]`), а не на уровне чека:

```json
{
  "type": "position",
  "name": "Сигареты X",
  "price": 14500,
  "quantity": 1,
  "measurementUnit": "шт",
  "paymentSubjectType": "товар подлежащий маркировке",
  "industryInfo": {
    "type": "additionalAttribute",
    "name": "Отраслевой реквизит",
    "value": [
      {
        "id": "1260",
        "value": {
          "1262": "030",
          "1263": "21.11.2023",
          "1264": "1944",
          "1265": "UUID=...&Time=...&Inst=...&Ver=2.0"
        }
      }
    ]
  }
}
```

**Важные замечания по PIOT §6.3:**
- **Тег 1262 = «030»** — ИД ФОИВ. Для маркировки это код **ФНС**. Уточнить у Атол: не должен ли быть `"030"` или другой код (по моему опыту, 030 — это ФНС, но для разных товарных групп могут быть разные ФОИВ — например, Росалкогольрегулирование).
- **Тег 1263 = дата документа** — **ISO или ДД.ММ.ГГГГ?** В ФФД обычно `ДД.ММ.ГГГГ`, но у Атол может быть ISO. Уточнить.
- **Тег 1264 = номер документа** — для маркировки это обычно номер постановления/приказа. **Откуда берётся?** Нужно зашить в конфиг или получать из ГИС МТ.
- **Тег 1265 = audit trail** — критично. Формат: `UUID=<reqId>&Time=<reqTimestamp>&Inst=<inst>&Ver=<version>`.
  - Онлайн: без `Inst` (по методичке v17, `Inst` — только для офлайна).
  - Офлайн: с `Inst` и `Ver`.

**Если официальный пример не получен до Шага 2 — в SPEC оставить плейсхолдер** `<INSERT_ATOL_OFFICIAL_EXAMPLE>` и явный запрет «не изобретать семантику». В код (Шаг 3) не переходить.

### Q4. Доступ к sandbox

**Ключевое уточнение, которого нет в плане:**

**«Sandbox» для онлайн ГИС МТ и для ЛМ ЧЗ — это два разных контура:**

| Контур | Что это | Как получить |
|--------|---------|--------------|
| **ГИС МТ sandbox** | Облачный тестовый контур ЧЗ (`https://markirovka.sandbox.crptech.ru`) | Заявка через ЛК ЧЗ → «Техподдержка» → «Доступ к тестовому контуру» |
| **ЛМ ЧЗ sandbox** | **Локально установленный** модуль ЛМ ЧЗ 2.0 на тестовом хосте | Скачать дистрибутив с `chestnyznak.ru`, установить на VM/сервер, инициализировать с токеном ГИС МТ sandbox |
| **ЕСМ / ТС ПИоТ** | Локально на кассе (для офлайн-авторизации через Token) | Установить дистрибутив ЕСМ ≥ 1.6.2.0 на тестовую кассу |

**Что делать:**
1. Для **онлайн** — запросить доступ к `markirovka.sandbox.crptech.ru` + тестовый X-API-KEY.
2. Для **офлайн** — развернуть ЛМ ЧЗ на тестовой VM (Ubuntu 22.04 — рекомендация методички). Получить тестовый токен от ГИС МТ sandbox.
3. Для **интеграции в чек** — тестовая ККТ на ФФД 1.2 с включённым «Торговля маркированными товарами» + ЕСМ ≥ 1.6.

**Без ЛМ ЧЗ на тестовом стенде Шаг 3 (код) не имеет смысла начинать** — тесты офлайн-ветки будут невозможны.

### Q7. `X-API-KEY` на `/cdn/health/check`

**Определённый ответ: вариант A — health-check вызывается ПОСЛЕ получения токена.**

Обоснование:
- Все endpoint'ы CDN API ГИС МТ (`/cdn/info`, `/cdn/health/check`, `/codes/check`) требуют `X-API-KEY` (методичка v17, раздел 1.4).
- Токен получается **не через CDN**, а через отдельный endpoint `/api/v3/true-api/auth/permissive-access` (или из ЛК ЧЗ вручную).
- `/auth/permissive-access` **не требует CDN** — это прямой вызов к ГИС МТ. Поэтому циклической зависимости нет.

**Правильный порядок вызовов:**
```
1. GisMtAuthService::ensureToken()
   → POST /api/v3/true-api/auth/permissive-access (или из .env)
   → получить X-API-KEY, expires_at

2. CdnService::getPlatforms()
   → GET /cdn/info (с X-API-KEY)
   → список хостов

3. CdnService::selectBest()
   → GET /cdn/health/check на каждый хост (с X-API-KEY), таймаут 2с
   → выбрать минимальный avgTimeMs

4. CodeCheckService::check()
   → POST /codes/check на выбранный хост (с X-API-KEY)
```

**Что добавить в план (критично):**
- **Отдельный случай: 401 на health-check.** Это **не** «CDN down», а «токен истёк». Должен быть **отдельный код ошибки** и **отдельная реакция** — обновить токен и повторить, а не помечать CDN как нерабочий.
- **Тестовый сценарий:** «просроченный токен → health-check 401 → рефреш токена → повтор health-check → успех».
- **Метрика:** количество 401 на health-check. Если > 0 — алерт (токен не обновляется).

**Вариант B (unauthenticated health endpoint)** — уточнить у Оператора ЧЗ. В методичке v17 явного такого endpoint нет. **Вариант C — избыточен** и создаёт путаницу.

### 2.3. Неточности в текущем плане (🟡)

**1. Блок 1.5, поле `status ENUM('pending','done','skipped','failed')`.**
Не описано, **кто и когда** ставит `skipped`. Гипотеза: отмена чека до фискализации? Возврат после фискализации? Нужно явно:
- `skipped` — чек отменён до фискализации, `/cis/sell` не нужен.
- `failed` — исчерпаны retry, нужен алерт.
- **Дополнительно:** для возврата после фискализации — не `skipped`, а **отдельная запись** в `marking_sell_queue` со статусом `return` (или отдельная таблица `marking_return_queue`).

- `error_code INT`,
- `package_type VARCHAR(20)`,
- `cdn_host VARCHAR(255)`,
- `response_time_ms INT`,
- `order_id BIGINT`,
- `check_id BIGINT`.

**3. Блок 3.5, `Check.php` — `addMarkingAttributes(item, markingResult)`.**
Сигнатура не учитывает, что на одну позицию может приходиться **несколько КМ** (например, 10 пачек в чеке — 10 КМ). Нужно:
```php
addMarkingAttributes(array $items, MarkingCheckResult $result)
```
где `$result` содержит результат **по каждому КМ**, и внутри метода идёт сопоставление `item ↔ КМ` (по `item_id`).
