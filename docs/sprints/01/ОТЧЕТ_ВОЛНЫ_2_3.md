## 2. Закрытые находки

### 2.1 2.1 🔴 — `process_returns.php` без идемпотентного retry

**Было:** `SellWorker` (волна 2.2) перед retry сверял `/cis/sold` и исключал уже
зарегистрированные КИ; у return-воркера симметрии не было: повторный `POST /cis/returned`
после потерянного ответа ЛМ ЧЗ → двойная обработка возврата (вариант B) или лишний алерт
(вариант A).

**Стало:**
- новый `Service/Marking/ReturnWorker` (симметрия `SellWorker`): при `attempts > 1` перед
  `/cis/returned` — сверка `/cis/sold`: КИ, **не числящиеся проданными**, — возврат применён
  предыдущей попыткой → повторно НЕ отправляются; ничего не числится → done БЕЗ вызова
  (`marking_return_already_applied_total`); частичный → returned только остаток
  (`marking_return_idempotent_skip_total`);
- `process_returns.php` переписан под worker (claim-цикл + re-claim guard как в
  `process_sells.php`);
- `marking_return_queue` — колонка `attempts` (DDL + миграция + SqliteDb): число claim'ов,
  симметричный reclaim (attempts >= max → failed + processed_at), `setStatus(id, ...)`;
- ошибка при attempts < max → pending БЕЗ +1 (инкрементит claim) — ровно `max_attempts`
  обработок строки.

Тесты: новый `ReturnWorkerTest` (26 ассертов, 6 сценариев), `WorkerStaleReclaimTest`
(кейсы 7/7b: return-attempts + return-зомби attempts=max → failed).

### 2.2 2.2 🔴 — HTTP 203 от /codes/check (online-only) не активировал emergency state

**Было:** `marking_emergency_state` активировался только в hybrid-ветке (COMMENTS-11 #2);
`CdnService` при 203 ставил лишь флаг + метрику + лог — в online-only режиме аварийный
режим ГИС МТ НЕ включался (и на /cdn/info, /cdn/health/check тоже).

**Стало:** централизованная точка `CdnService::onEmergency203(endpoint, host)` — 203 на
**любом** endpoint ГИС МТ (`/codes/check`, `/cdn/info`, `/cdn/health/check`) → метрика
`marking_emergency_total` + лог `cdn_emergency_203` + `MarkingEmergencyState::activate(ИНН,
'HTTP 203 …')`. Инжекция `MarkingEmergencyState` в конструктор `CdnService` (4-й параметр,
deferred — тесты); `MarkingCheckService::cdn()` (prod) передаёт свой emergency-state.
Отсутствие ИНН/БД — не блок (warn-логи `emergency_state_no_inn` /
`emergency_state_activate_failed`). Hybrid-ветка (raw-запрос, не CdnService) — без изменений;
двойного счёта метрики нет.

Тесты: `CdnServiceTest` +8 ассертов (203 /codes/check → activate по ИНН + метрика; 203
/cdn/info → activate + хосты всё же парсятся).

### 2.3 2.3 🟠 — `marking_emergency_state` не имеет auto-expire

**Было:** аварийный режим по ИНН, однажды активированный, оставался активным вечно до
ручного `confirmEnd()` — после восстановления ГИС МТ касса продолжала ходить в аварийный
allowAll-режим (fail-open).

**Стало:** `MarkingEmergencyState::expireIfStale()` (вызывается в начале
`MarkingCheckService::check()`, try/catch — БД недоступна не блок):
- `actual_end_at` задан (оператор подтвердил окончание) И ему > 3 суток → `is_active=0`;
- `actual_end_at` NULL и режим активен > 7 суток → `is_active=0`,
  `actual_end_at = started_at + 7 суток` (метка авто-expire);
- метрика `marking_emergency_auto_expired_total` + ERROR-лог `emergency_auto_expired`.

Техническое примечание (принято при реализации): пороги считаются в PHP
(`col < :staleNow`), а не в SQL (`col + 7*86400 < :now`) — в эмулированном PDO SQLite
сравнение выражения с bound-параметром упорядочивается как INTEGER < TEXT (найден в тестах;
см. `ИТОГИ_ВОЛНЫ_2.md` §6.12).

Тесты: `MarkingEmergencyStateTest` кейс 6 (свежий / >7 суток / >3 суток / <3 суток),
`MarkingCheckServiceTest` кейс 16 (check() вызывает expireIfStale).

### 2.4 2.4 🟠 — `LEASE_MINUTES=15` и `max_attempts=3` — хардкод в двух местах

**Было:** константы `LEASE_MINUTES`/`DEADLOCK_MAX_ATTEMPTS` + `static $max_attempts` в
`MarkingSellQueue` И `MarkingReturnQueue` (дублирование).

**Стало:** config-секции `sell_queue`/`return_queue` в `config/marking.php`
(`lease_minutes`, `max_attempts`, `deadlock_max`; env `MARKING_LEASE_MINUTES`,
`MARKING_MAX_ATTEMPTS`, `MARKING_DEADLOCK_MAX`; default 15/3/5 — сохранены значения волны 2.2);
модели: `leaseMinutes()`/`maxAttempts()`/`deadlockMaxAttempts()` (test-override —
`self::$max_attempts > 0`); константы удалены; `.env.example` — новые переменные.

Проверка (COMMENTS-12): grep `LEASE_MINUTES` в `Models/` → 0 совпадений; default — в config.

### 2.5 2.5 🟠 — `activate()` не идемпотентна при гонке двух воркеров

**Было:** DELETE+INSERT в транзакции; если второй воркер успел вставить строку между DELETE
и INSERT → UNIQUE-конфликт по `inn` → `PDOException` → второй воркер падал (в production —
500/крах прогона).

**Стало:** портативный эквивалент `ON DUPLICATE KEY UPDATE` (он сам не портативен — MySQL
only): при UNIQUE-конфликте (SQLSTATE 23000 / «Duplicate entry» / «UNIQUE constraint
failed») — один повтор DELETE+INSERT (`isDuplicateKey()`), без падения. Повторный activate
обновляет `started_at`/`reason` (новый период аварийного режима).

Тест: `MarkingEmergencyStateTest` кейс 5 (повторный activate — одна строка, обновлённые
started_at/reason; гонка эмулируется повторным вызовом — контракт «один retry при
конфликте» закреплён в `activate()`).

### 2.6 2.6 🟡 — нет метрики идемпотентного пропуска sell

**Стало:** `SellWorker`: retry обнаружил КИ в `/cis/sold` и пропустил `/cis/sell` →
метрика `marking_sell_idempotent_skip_total` (+= число пропущенных КИ) — для мониторинга
«сколько повторных /cis/sell не ушло благодаря сверке».

### 2.7 2.7 🟡 — `FakeEmergencyState` без reset()

**Стало:** `FakeEmergencyState::reset()` (active/calls/reasons/expires) + override
`expireIfStale()` (no-op без БД — иначе parent полез бы в MySQL-DSN). Инстансы в тестах
создаются по одному на сценарий (`mcs_service()`); `reset()` — для переиспользуемого фейка.

Тест: `MarkingCheckServiceTest` кейс 17.

### 2.8 2.8 🟡 — кап /cis/sold (5000) — слабая защита, нет алерта

**Стало:** кап повышен до **10000 КИ** (100 страниц по 100 — лимит ЛМ ЧЗ 100/запрос) в
обоих воркерах (`SellWorker`, `ReturnWorker`); при исчерпании — метрики
`marking_sell_sold_cap_exceeded_total` / `marking_return_sold_cap_exceeded_total`
(+= число непроверенных КИ строки) + WARN-лог `sell/return_sold_scan_cap_exceeded`
(неизбежная повторная отправка — алерт оператора, SPEC §5).

Тест: `ReturnWorkerTest` кейс 6 (total 20000 → цикл упирается в кап → метрика 2.0).

## 4. Семантические изменения (важно для оператора/деплоя)

1. **`marking_return_queue` получает `attempts`** — при развёртывании существующей БД нужна
   миграция `ALTER TABLE ... ADD COLUMN attempts INT UNSIGNED NOT NULL DEFAULT 0` (в
   `sql/marking_tables.sql`). Зомби-строки с attempts=0 после деплоя reclaim'ятся как
   pending — повторный `/cis/returned` идемпотентен через сверку `/cis/sold`.
2. **Параметры очередей — из `.env`** (`MARKING_LEASE_MINUTES`/`MARKING_MAX_ATTEMPTS`/
   `MARKING_DEADLOCK_MAX`, default 15/3/5) — настройка без правки кода.
3. **HTTP 203 теперь везде включает аварийный режим ГИС МТ** (не только гибрид):
   последующие проверки — allowAll по ИНН до `confirmEnd()` ИЛИ авто-expire (см. 4).
4. **Аварийный режим авто-expire'ится**: > 7 суток без подтверждённого окончания (ИЛИ > 3
   суток после confirmation) — `is_active=0` + метрика `marking_emergency_auto_expired_total`
   + ERROR-лог. Оператору это видно в KPI/алертах (SPEC §5).
5. **Повторные `/cis/returned` исключены на уровне кода** (сверка `/cis/sold` при
   attempts > 1), как и повторные `/cis/sell` (волна 2.2).

## 7. Ограничения и примечания

1. **Кап выгрузки `/cis/sold` — 10000 КИ** (по одному воркеру): КИ строки за пределами
   выгрузки не проверяются — для sell они отправятся повторно (ЛМ ЧЗ отклонит как дубль),
   для return — считаются «возвратом применёнными» и пропускаются; оба случая заалертены
   метриками `*_sold_cap_exceeded_total` (2.8).
2. **Lease / max_attempts / deadlock_max** — из config, но НЕ из БД (static-модели читают
   config в момент вызова; test-override через `Marking*Queue::$max_attempts`).
3. **`expireIfStale()` — в `check()`** (каждая проверка кодов), а не в cron: дешёвый UPDATE
   по индексу, стоимость пренебрежима; cron-вызывание не требуется (COMMENTS-12 «или вызов
   раз в час через cron» — реализовано проверкой в `check()` как обязывающий путь).
4. **Race-safe `activate()`** — один повтор при UNIQUE-конфликте; при перманентном
   конфликте (не UNIQUE) исключение пробрасывается (поведение как в волне 2.2 — вызывающие
   точки обёрнуты try/catch).
5. **Mock-интеграция** не покрывает lease/attempts/return-worker напрямую — детерминированные
   гонки на однопроцессном CLI-сервере ограничены; эти ветки покрыты unit-тестами
   (`ReturnWorkerTest`, `WorkerStaleReclaimTest`).
6. Внешние блокеры (JSON Атола — Q3, живой ЛМ ЧЗ, sandbox-токен — Q4a, регионы — Q2a,
   письменное утверждение SPEC) — без изменений.
