## 2. Критические правки (🔴)

### 2.1. Тег 1260: план изобретает семантику, противоречащую PIOT-докам 🔴

**Блок 1.2** предлагает такую структуру:
```json
"industryInfo": {
  "attribute": [{
    "attribute": [
      {"tag": "1262", "name": "Группа товаров",  "value": "12"},
      {"tag": "1263", "name": "Особый статус",   "value": "ok"},
      {"tag": "1264", "name": "Строка статуса",  "value": "<statusString>"},
      {"tag": "1265", "name": "Метод проверки",  "value": "ONLINE|OFFLINE|HYBRID"}
    ]
  }]
}
```

**Но в исходном PIOT-документе (`Анализ документации PIOT...txt`, §6.3) сказано:**
```
Тег 1260:
  1262 = "030"                    # ИД ФОИВ
  1263 = "21.11.2023"             # Дата документа основания
  1264 = "1944"                   # Номер документа основания
  1265 = "UUID=...&Time=...&Inst=...&Ver=..."  # Значение
```

Это **две разные семантики**. План заменяет:
- 1262 «ИД ФОИВ» → «Группа товаров»
- 1263 «Дата документа» → «Особый статус»
- 1264 «Номер документа» → «Строка статуса»
- 1265 «UUID+Time+Inst+Ver (метаданные проверки)» → «ONLINE/OFFLINE/HYBRID»

**Проблема:** тег 1265 в оригинале несёт **audit trail** — UUID проверки, время, инстанс ЛМ ЧЗ, версию. Это то, что ФНС/ГИС МТ может проверить пост-фактум. Заменять его на строку `ONLINE` — **терять аудит**, что нарушает требования методички.

**Что нужно:**
1. **Не изобретать семантику.** Взять официальный пример JSON от Атол (ДККТ 10.10.8.24) — это и так в открытых вопросах (Q3), но в блоке 1.2 нужно **не писать пример со своей семантикой**, а оставить плейсхолдер «вставить официальный пример».
2. Если 1262–1264 действительно имеют такое значение в текущей версии ФФД — задокументировать **источник** (номер приказа ФНС, раздел методички, страница).
3. 1265 **обязательно** должен содержать `UUID=...&Time=...&Inst=...&Ver=...`, независимо от того, был это ONLINE или OFFLINE. Для ONLINE — без `Inst` (по методичке v17), для OFFLINE — с `Inst` и `Ver`.
4. Уровень (`item`) — **верно**, это критично. Но вложенность `industryInfo.attribute[].attribute[]` выглядит подозрительно (двойной `attribute`). Обычно это `industryInfo: { attribute: [...] }`, а не вложенный массив. Уточнить по официальному примеру.

**Приоритет:** 🔴 — без этого чек не примет маркировку.

### 2.2. Табачные КМ: §2.1 предлагает несуществующее поведение API 🔴

**Блок 2.1** предлагает:
> «При продаже блока: отправить **один** запрос с `packageType=GROUP` и списком КИ единиц.»

**Проблема:** API `/codes/check` не принимает «packageType=GROUP с вложенным списком КИ единиц». Он принимает **плоский массив `codes`**. Каждый код проверяется независимо.

**Реальная логика (из методички, п.6):**
- При продаже **блока** — отправляем КМ блока, получаем результат с `packageType=GROUP` и полем `parent` (или наоборот — `parent` заполнен у дочерних).
- При продаже **пачки** — отправляем КМ пачки, получаем `packageType=UNIT`.
- **Запрет:** одновременная продажа агрегата и входящих в него единиц. Проверяется **локально**: из результатов достаём `cis` всех агрегатов и `parent` всех единиц; если есть пересечение — `BLOCK`.

**Что нужно переписать в §2.1:**
```
- Отправляем плоский список всех КМ чека в /codes/check.
- Из ответа извлекаем (cis, packageType, parent) по каждому.
- Локальная проверка: 
  - Собрать set агрегатов = {r.cis : r.packageType in [GROUP, BUNDLE, PRODUCT_SET]}
  - Собрать set родителей единиц = {r.parent : r.packageType == UNIT}
  - Если intersection не пусто → SaleProhibition::BLOCK («одновременная продажа агрегата и вложенных единиц»).
```

### 2.3. HTTP 203: «3 дня после» — от чего считать? 🔴

**Блок 1.4** пишет: «На период `emergencyMode` и **3 дня после** все проверки отключаются».

**Не указано:**
- 3 дня после **чего**? После получения 203? После последнего 203? После официального объявления окончания аварии Оператором?
- Если касса получила 203 в 23:59, а Оператор объявил окончание в 00:05 — считаем ли мы «3 дня после окончания» или «3 дня после первого 203»?

**Что нужно (по методичке §7):**
- Авария вводится Оператором, Оператор же её завершает (email/ЛК/сайт).
- Пока `emergencyMode=true` — проверки отключены.
- После завершения — **ещё 3 дня** от **даты завершения** (не от даты 203).
- Отслеживать в конфиге/БД: `emergency_started_at`, `emergency_expected_end_at`, `emergency_actual_end_at`.
- Если `emergency_actual_end_at` не получен (нет email) — считать от `emergency_started_at + 3 дня` с алертом «нужно подтверждение окончания».

**Приоритет:** 🔴 — иначе касса может «залипнуть» в emergency или выйти из него слишком рано.

### 2.4. `X-API-KEY` на `/cdn/health/check` — остался неразрешённым 🔴

Это было в моём предыдущем ревью (§3.2), и в плане **не упоминается**.

**Проблема:** если `/cdn/health/check` требует `X-API-KEY`, а токен истёк — мы не можем ни проверить здоровье CDN, ни выбрать площадку, ни обновить токен (циклическая зависимость). По актуальной методичке health-check **не должен** требовать токен.

**Что нужно:** добавить в блок 6 (открытые вопросы) и в блок 1 (критические):
- Q7: требует ли `/cdn/health/check` заголовок `X-API-KEY`?
- Если да — предусмотреть fallback: пробовать без токена; при 401 — использовать дефолтный список CDN.

## 3. Важные замечания (🟠)

### 3.1. `marking_check_history` — не хватает ключевых полей

**Блок 2.4** предлагает схему:
```sql
request_id, code, found, verified, sold, is_blocked, prohibition, created_at
```

**Пробелы:**
- Нет `cis` отдельно от `code` (КМ ≠ КИ; для табака это разные строки).
- Нет `source ENUM('ONLINE','OFFLINE','HYBRID')` — критично для аудита race-условия.
- Нет `error_code` (0–11) — нужно для отладки.
- Нет `package_type` — нужно для локальной проверки агрегатов.
- Нет `cdn_host` — при переключении CDN между запросами.
- Нет `response_time_ms` — для SLA.
- Нет `prohibition_level` — только `ALLOW/WARN/BLOCK`, но методичка различает ещё INFO.
- Нет `order_id` / `check_id` — для связи с чеком.

**Что нужно:** расширить схему и явно указать, что пишется на **каждый** КМ (а не на запрос).

### 3.2. Batch size 100 — для `/codes/check` может быть меньше

**Блок 2.5:** «до 100 КМ за запрос». По методичке v17 лимит на `/codes/check` — **не более 100**, но иногда ограничение **30** для тестового контура. Уточнить по актуальной методичке и сделать **настраиваемым параметром** (`config('marking.code_check.batch_size')`).

### 3.3. `Order::getMarkingCodes()` — источник не определён

В моём предыдущем ревью (§3.6) это было отмечено, и план **не закрывает** этот вопрос. Даже в блоке 3.5 (Check.php) — только про добавление атрибутов, но не про то, откуда берутся КМ.

**Что нужно добавить:**
- Схема хранения КМ в заказе: отдельная таблица `order_marking_codes(order_id, item_id, raw_code, cis, gtin, pg, scanned_at)` или JSON-поле.
- Кто и когда заполняет (сканер кассира? импорт?).
- Что если в заказе 2 пачки одного товара — 2 разных КМ.

### 3.4. `timeZone` — не закрыт (блок 3.4)

**Блок 3.4** просто говорит «уточнить у заказчика». Это не решение — это откладывание. В SPEC нужно **явно** описать:
- Либо `timeZone` берётся из конфига кассы (`Cassa::getTimeZone()`).
- Либо из глобального конфига с override per-cassa.
- Либо жёстко 2 (MSK) — только если все магазины в MSK.
- **Валидация:** 1..11, иначе ошибка конфигурации.
