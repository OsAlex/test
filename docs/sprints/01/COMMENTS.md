Ниже — разбор трёх документов (анализ, SPEC Фаза 1, SPEC Фаза 2) с точки зрения реализуемости, внутренней согласованности и соответствия методичке v17. Разделил на **критические** (блокеры/баги), **важные** (нужно уточнить до старта) и **мелкие** (косметика/UX).

## 2. Критические замечания

### 2.1. Смешение «предупреждений» и «запретов продажи» 🔴

**Фаза 1, §2.4.2** в таблице запретов для случая 1 пишет:
> `found=false` ИЛИ `utilised=false` → запрет

Но **Приложение 2 методички** (тест-кейсы 1 и 2 в §6 Фазы 1) явно указывает:
- `utilised=false` → **Предупреждение**
- `realizable=false, utilised=true, sold=false` → **Предупреждение**

**Аналогично** для `errorCode` 1–9 в §2.3.3 сказано «Предупреждение кассиру», но §2.4.2 случай 2 `verified=false` называет запретом.

**Что нужно:** ввести единый enum `ProhibitionLevel { BLOCK, WARN, INFO }` и в SPEC зафиксировать, что именно:
- `found=false` или `sold=true` → **BLOCK** (нельзя провести чек)
- `verified=false`, `isBlocked=true` → **BLOCK** (методичка, п.4)
- `utilised=false`, `realizable=false`, `errorCode 1-9` → **WARN** (можно, но с предупреждением кассира)
- Просрочка (`expireDate`) → **BLOCK** для табака; для других — уточнить в методичке

Без этого кассир не сможет провести продажу там, где методичка разрешает.

### 2.2. Тег 1260 — структура в §5.2 Фазы 2 неверна 🔴

Сниппет:
```php
$info['items'][] = (object)[
    'type' => 'additionalAttribute',
    'name' => 'Отраслевой реквизит',
    'value' => (object)[
        'id' => '1260',
        'value' => (object)['id' => '1262', 'value' => '030'],
        // ...
    ]
];
```

**Проблемы:**
1. Тег 1260 в ФФД 1.2 — это **отраслевой реквизит предмета расчёта**, он относится к конкретному товару, а не к чеку целиком. Структура в коде похожа на реквизит чека (`additionalAttribute`).
2. В Атол API v2 отраслевой реквизит предмета расчёта передаётся **внутри объекта `item`** через массив `industryInfo` с полями `id`, `value`, а не через `additionalAttribute`.
3. Для ФФД 1.2 нужен **`ffdTag 1260` → вложенные 1262/1263/1264/1265** и именно у **каждого маркированного предмета расчёта**.
4. В теге 1265 для онлайн-проверки в методичке обычно и `Ver` присутствует (версия формата), даже когда онлайн. Уточнить по актуальной методичке.

**Что нужно:** получить официальный пример JSON от Атол (или из ДТО 10.10.8.24) с реальным чеком продажи табака и **отревьюить структуру тега 1260 по нему**. Иначе весь цикл чека будет падать на валидации ККТ.

### 2.3. `MarkingCheckService::checkHybrid` — race condition 🔴

В §2.3.1 Фазы 2 и §2.4.1 Фазы 1 описано:
- параллельно запускаем онлайн (таймаут 1.5с) и офлайн;
- «приоритет офлайн: если sold=true → запрет».

**Проблема:** если онлайн вернёт ответ за 1.4с (`sold=false`, OK), а офлайн за 1.6с (`sold=true`), мы уже приняли решение продать и зафиксировали чек. Откат — только через чек возврата, что нарушает п.5 методички.

**Что нужно:**
1. До старта проверки задать **жёсткий барьер**: ждём **оба** ответа до 1.5с; если офлайн не успел — считаем офлайн недоступным и решаем по онлайну.
2. Если офлайн приходит с `sold=true` **позже** 1.5с — обязательно логировать и алертить, но чек не откатывать (по методичке это уже вне SLA).
3. Для каждого КМ хранить `decisionSource: ONLINE | OFFLINE | FALLBACK` — это пойдёт в аудит.

### 2.4. Несовместимость DTO между Фазой 1 и Фазой 2 🔴

В Фазе 1 `MarkingCheckResult` содержит `results: MarkingCodeResult[]`, а в Фазе 2 оркестратор `checkHybrid` возвращает **тот же** `MarkingCheckResult`, но в §2.3.2 таблице запретов фигурируют поля `mrp`, `smp`, `isBlocked`, `sold`, `isGreyGtin`, `gtin` — их **нет** в `CodeCheckCodeResult` из Фазы 1 (там есть `mrp`, `smp`, `isBlocked`, `sold`, но нет `isGreyGtin`).

**Что нужно:** зафиксировать **единый** DTO `MarkingCodeResult`, который объединяет поля онлайн и офлайн:

```php
class MarkingCodeResult {
    public string $cis;
    public string $gtin;
    public ?bool $found;         // только онлайн
    public ?bool $valid;         // только онлайн
    public ?bool $verified;      // только онлайн
    public ?bool $realizable;    // только онлайн
    public ?bool $utilised;      // только онлайн
    public ?string $expireDate;  // только онлайн
    public bool $isBlocked;
    public bool $sold;
    public bool $isGreyGtin;     // только офлайн (в онлайне — через ogvs)
    public array $ogvs;          // только онлайн
    public ?int $mrp;
    public ?int $smp;
    public ?string $packageType;
    public ?string $parent;
    public string $decisionSource;  // ONLINE|OFFLINE|HYBRID
    public array $prohibitions;     // SaleProhibition[]
}
```

Это уберёт расхождение при интеграции.

### 2.5. Логика `/cis/sell` после фискализации — нет компенсации 🔴

В §5.1 Фазы 2:
```php
$result = $check->send();
// ...
foreach ($markingCodes as $code) {
    LmChzService::sell($code->getCis());
}
```

**Проблема:** если `sell()` упадёт (ЛМ ЧЗ лёг, 5xx, сеть), чек уже фискализирован, а КИ не в БД проданных. По методичке это критично: следующий чек с тем же КИ должен быть заблокирован, но не будет.

**Что нужно:**
1. Ввести **очередь отложенной регистрации**: если `sell()` не удался — писать в `marking_sell_queue` и повторять с backoff.
2. Алертить, если запись висит > N минут.
3. На время «в очереди» — **блокировать** этот КИ локально (свой мини-список), чтобы повторно не продать.

### 2.6. `timeZone` — источник значения не определён 🔴

В §2.3.1 Фазы 1: `timeZone: 1..11 // défaut: 2 (МСК)`. Но:
- Часовые пояса РФ: Калининград (1) … Камчатка (11). **Как определять для конкретной кассы?**
- Если магазин в Калининграде, а `timeZone=2` — `smp`/`mrp` вернутся по МСК, что повлияет на проверку цены ниже МРЦ (товарная группа 3, АТП id=12).

**Что нужно:** либо брать из конфига кассы, либо из геолокации, либо явно вынести в `Cassa::getTimeZone()`. Прописать в SPEC.

## 3. Важные замечания

### 3.1. Обработка HTTP 203 — нет в функциональных требованиях

Упоминается в §7 DoD Фазы 1 как «флаг отключения проверок», но **нет описания**:
- Что означает 203 (аварийная ситуация на стороне ГИС МТ)?
- На 3 дня отключаются только онлайн-проверки или вся логика?
- Нужно ли уведомлять кассира? Логировать в отдельный канал?
- Как потом возобновлять (по таймеру, по письму от Оператора)?

**Что нужно:** отдельный раздел «Аварийные ситуации» с псевдокодом.

### 3.2. `X-API-KEY` на `/cdn/info` и `/cdn/health/check`

В §2.1.1 и §2.1.2 указано, что нужен `X-API-KEY`. В методичке v17 для health-check **аутентификация не требуется** (иначе при истёкшем токене мы не сможем выбрать CDN). Нужно уточнить по актуальной методичке — иначе получим циклическую зависимость: чтобы проверить токен, нужен CDN, а чтобы выбрать CDN, нужен токен.

### 3.3. Оценка `avgTimeMs` — не указан порог

В §2.1.3 «выбор по минимальной latency». Но:
- Порог «плохой» latency? Если все CDN отвечают 800 мс — это ок?
- Как учитывать «свежесть» замеров? 5 минут назад CDN был 50 мс, сейчас 500 мс.
- Кэшировать ли `avgTimeMs` и на сколько?

### 3.4. Нет спецификации `MarkingCode::extractCis` для агрегатов

§2.2.1 Фазы 2 описывает общий случай и табак, но:
- Что с агрегатами (`packageType=GROUP`)? В КМ агрегата может быть **несколько КИ** (вложенных).
- Что с `BUNDLE` и `PRODUCT_SET`?
- Где хранится `pg` (товарная группа) для `outCheck`? Нужно мапить из товара заказа.

### 3.5. `/cis/sold` — пагинация и назначение

§2.1.8: `skip`, `limit` до 1000. Но:
- Для чего именно используется в проекте? (резервное копирование — сказано, но куда?)
- Кто вызывает? Cron? По расписанию?
- Что делать при рассинхроне локальной БД и ЛМ ЧЗ?

### 3.6. Отсутствует описание `Order::getMarkingCodes()`

В §5.1 Фазы 2 вызывается `$check->getOrder()->getMarkingCodes()`, но:
- Откуда берутся КМ? Из таблицы товаров заказа? Из сканирования кассиром?
- Формат хранения (одна КМ на строку? массив в JSON-поле?).
- Что если в заказе 2 единицы одного товара — оба КМ надо проверять?

### 3.7. `make_json($tag1260Data)` — ломает сигнатуру

В Фазе 2 §5.1 и §3.2 (анализ) предлагается расширить `make_json()` аргументом. Это **breaking change** для всех текущих вызовов. Нужно:
- Либо перегрузка с дефолтным `null`;
- Либо отдельный `withTag1260(array $data)` билдер;
- Либо хранить `tag1260` в самом `Check` (свойство) и читать в `make_json()`.

### 3.8. Rate limiting для History API

§2.3.4 Фазы 1: 1 запрос/мин. Но **не описано**:
- Как встроить в общий цикл чека (нельзя ждать минуту).
- Очередь на отправку истории (Redis? таблица?).
- Что делать, если за минуту накопилось 500 reqId (лимит 100 за раз).

### 3.9. `ogvs` в офлайне — противоречие

§2.3.2 Фазы 2 в примечании: «в офлайне недоступны ... `ogvs`», но случай 4 таблицы запретов: `isBlocked=true` + `ogvs указывает ОГВ`. Если `ogvs` нет — как понять, что блокировка именно от ОГВ, а не что-то ещё? Похоже, в офлайне `isBlocked=true` уже сам по себе означает блокировку ОГВ. Уточнить формулировку.

### 3.10. ФН-М и формат `fiscalDriveNumber`

В §2.3.1 Фазы 1 `fiscalDriveNumber: "16 цифр ФН"`. Но:
- ФН-М (новый формат) — тоже 16 цифр? Или 15?
- Что передавать, если на кассе ФН-М?
- Валидация: 16 цифр обязательна?

## 4. Мелкие замечания

1. **§2.2.2 Фазы 1**: «при 401 — попытка обновить через `/cdn/info`» — `/cdn/info` не выдаёт токен. Должно быть `/auth/permissive-access` или ручное обновление.
2. **§1.2 анализа**: «Срок действия токена продлён до 01.10.2026» — но в SPEC указан `token_expires = '2026-10-01'` без года в формате даты. Мелочь.
3. **§2.1.2 Фазы 1**: «`Connection: close`» для health-check — хорошо, но не описано, как это реализовать в curl (`CURLOPT_FORBID_REUSE`).
4. **§2.1.4 Фазы 2**: пример ответа `outCheck` содержит `mrp`/`smp` — но не указано, всегда ли они приходят или только для табака/НСП.
5. **§2.2.1 Фазы 2**: «29 символов» для табака — но в примере `00000046233219!SX-RqRADpU7Cev` длина 29, и берётся первых 21. Проверить, что это правило не сломается на новых КМ.
6. **§5.2 Фазы 1**: DTO `CodeCheckResponse` содержит `reqId` и `reqTimestamp` — но в ответе `/codes/check` из методички они могут называться иначе (`requestId`?). Уточнить по реальному ответу sandbox.
7. **§2.3.2 Фазы 1**: таблица полей ответа содержит `soldUnitCount`, `innerUnitCount`, `eliminationState`, `message` — в таблице п.136 они есть, но в тексте SPEC не описано их назначение. Добавить комментарии.
8. **§6 Фазы 1**: тест «HTTP 500 (code 5000)» — не сказано, сколько retry.
9. **§3.1 Фазы 2**: требования к ОС — но нет требования к **Java** (ЛМ ЧЗ — JVM-приложение) или другим зависимостям.
10. **§2.1.3 Фазы 2**: поле `inst` — это UUID инстанса, но не сказано, совпадает ли он с `inst` в ответе `outCheck` (для тега 1265). Нужно явно связать.
