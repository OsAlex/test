## 2. Закрытые проблемы

### 2.1 #1 🔴 — Heartbeat не обновлялся во время обработки (race возвращался)

**Было (волна 2.1):** `heartbeat_at` = last-seen; воркер ставил метку один раз после claim,
далее уходил в HTTP-вызов ЛМ ЧЗ. При обработке длиннее stale-порога (10 мин) второй воркер
reclaim'ил строку, которую первый ещё активно обрабатывал → двойной `/cis/sell` по одному КИ.

**Стало — lease semantics:**
- `heartbeat_at` — **момент истечения LEASE** (не last-seen): `claimNextPending()` и
  `extendLease()` ставят `NOW + LEASE_MINUTES` (15 мин, константа модели);
- reclaim «зомби» — только при истёкшем lease: `heartbeat_at < NOW` или `NULL`
  (NULL — legacy/переходные строки, в т.ч. last-seen-метки волны 2.1: они reclaim'ятся
  на первом запуске после деплоя — консервативный transition);
- воркер **продлевает lease** (`extendLease()`) перед каждым потенциально долгим вызовом
  (outCheck/sell в `SellWorker`, `/cis/returned` в `process_returns.php`) — активная
  обработка не отснимается при любом времени HTTP-вызова;
- return-очередь — то же самое (там нет attempts; зомби → pending).

Файлы: `Models/MarkingSellQueue.php`, `Models/MarkingReturnQueue.php` (reclaim по истёкшему
lease, `extendLease()`, `LEASE_MINUTES=15`), `docs/sprints/01/sql/marking_tables.sql`
(комментарии DDL + примечание transition), `Service/Marking/process_returns.php`,
`Service/Marking/SellWorker.php`.

Тест: `WorkerStaleReclaimTest` — переписан на lease (9 групп, 25 ассертов): lease в будущем
после claim, истёкший lease подхватывается другим воркером (кейс из spec), активный lease
не снимается, attempts-инкремент в claim, `extendLease()` только для processing, legacy NULL.

### 2.2 #2 🟠 — HTTP-ошибки в hybrid-ветке не покрыты тестами

**Было:** условие `$http->status < 500` допускало 4xx в parse-ветку (тела отсекались в
`parseOnlineResponse`, но фильтрация была неявной); 203 парсился, но **не активировал**
аварийный режим и мог «утонуть» в merge с офлайн-веткой.

**Стало (комментарии в `Service/Marking/MarkingCheckService::checkHybrid`):**
- обе ветки учитывают **только 2xx** (`HttpResponse::ok()` = 200..299 и без транспортной
  ошибки); 4xx/5xx-тела не парсятся (500 с JSON «error» не превращается в результат),
  ветка отбрасывается — решение по оставшейся ветке; 401 онлайн — отдельная ветка
  (метрика `marking_401_total`, офлайн остаётся);
- **HTTP 203 (аварийный режим ГИС МТ):** новый `activateEmergency203()` —
  `MarkingEmergencyState::activate(ИНН, 'HTTP 203 от CDN-хоста …')` + метрика
  `marking_emergency_total` + лог `hybrid_online_203` (БД/отсутствие ИНН — не блок),
  результат — `source = EMERGENCY` **без merge** с офлайн-веткой (при невалидном теле 203 —
  `allowAll`); правило §3.5 (агрегат + единицы при недоступном онлайн → BLOCK) применяется.

Тест: `MarkingCheckServiceTest` кейсы 14–15 (+7 ассертов → 51): 500 online + 200 offline →
OFFLINE (офлайн-ответ учтён, чужое тело не распарсилось); 203 + офлайн → EMERGENCY,
`activate()` вызван для ИНН с причиной «203», метрика += 1. `FakeEmergencyState` получил
переопределённый `activate()` + `$reasons`.

### 2.3 #3 🟠 — Double-продажа (повторный `/cis/sell`) при retry

**Было:** при сбое между `sell()` и `markDone()` retry отправлял те же КИ в `/cis/sell`
повторно (response KKT мог уйти до сбоя → дубль).

**Стало:** логика обработки строки вынесена из `process_sells.php` в новый класс
`Service/Marking/SellWorker` (тестируемый; `process_sells.php` — только claim-цикл):
- при `attempts > 1` (claim уже инкрементировал attempts, #1) перед `/cis/sell` —
  **сверка `/cis/sold`**: пагинация по 100 (лимит ЛМ ЧЗ), пересечение с КИ строки,
  компромисс задокументирован: кап 5000 выгруженных КИ;
- КИ, уже зарегистрированные ЛМ ЧЗ предыдущей попыткой, повторно не отправляются;
  отправляется только остаток;
- всё уже продано → `done` **без вызова sell** (причина в `error`: «КИ зарегистрированы
  ЛМ ЧЗ ранее»);
- ошибка при `attempts < max` → `pending` **без +1 к attempts** (инкрементит claim) —
  ровно `max_attempts` (3) обработок строки; `attempts >= max` → `failed` + `processed_at`;
- outCheck с CANCELLED → терминальный failed «КИ под запретом в ЛМ ЧЗ», sell не вызывается.

Файлы: `Service/Marking/SellWorker.php` (новый), `Service/Marking/process_sells.php`
(переписан под worker), `Service/Marking/LmChzService.php` (латентный warning
`Undefined array key "sold"` → `($raw['sold'] ?? null)` — зафиксирован при regeneration
verify-снапшота).

Тест: новый `tests/Unit/SellWorkerTest.php` (25 ассертов, 6 сценариев): новая строка →
sell(все) → done, attempts не растёт; retry — всё в `/cis/sold` → done без sell; частичный
sold → sell только остатка; ошибка sell → pending без +1; attempts=max → failed +
processed_at; CANCELLED → blocked.

### 2.4 #4 🟠 — `assertAtolExampleAvailable` без проверки «окружение вообще задано»

**Было (волна 2.1, COMMENTS-10 2.3):** только «unset + placeholder=0 → throw»; `staging`
и прочие значения неявно работали как dev.

**Стало (COMMENTS-11 #4, Variant B):** `APP_ENV` обязан быть ОДНИМ из
`dev | test | prod | production` (lowercase, trim); любое другое значение — включая
**НЕНАЗНАЧЕННЫЙ** и `staging` — → `RuntimeException` **до** остальных проверок;
mock-обёртка (placeholder=1) не освобождает от явного объявления окружения. Дальнейшая
логика неизменна: prod + placeholder=1 → throw (чек не уходит на ККТ); prod +
placeholder=0 → обязателен файл официального JSON.

Файлы: `Models/Check.php` (`assertAtolExampleAvailable`), `.env.example` (whitelist-комментарий).

Тест: `AtolPlaceholderGateTest` кейсы 5–8 (+4 ассерта → 12): unset+placeholder=0 → throw;
**unset+mock → throw** (ранее — «допустимо»); `staging` → throw с видимым значением в
сообщении; `test` → OK.

### 2.5 #5 🟡 — Backoff без экспоненты, только 3 попытки

**Было:** 3 попытки, линейный backoff 50/100 мс.

**Стало:** в обеих очередях (`MarkingSellQueue`/`MarkingReturnQueue`) — до **5** попыток
(`DEADLOCK_MAX_ATTEMPTS`), экспоненциальный backoff `50·2^(n−1)` (50/100/200/400 мс) +
jitter `random_int(0, 50)` мс; не-deadlock-ошибки пробрасываются сразу.

Тест: `WorkerStaleReclaimTest` кейсы 8–9: 3 deadlock-фейла → успех, фактическое время
≥ 300 мс (50+100+200), ровно 4 вызова claimOnce; deadlock > лимита → PDOException проброшен
после ровно **5** попыток.

## 4. Семантические изменения (важно для оператора/деплоя)

1. **Lease = 15 минут.** «Зомби» теперь определяется истечением lease, а не возрастом
   метки. Переходный период после деплоя: все processing-строки с timestamp в прошлом
   (включая последние 10 мин волны 2.1) reclaim'ятся на первом запуске воркера — повторная
   отправка `/cis/sell` идемпотентна за счёт сверки `/cis/sold` (п. 2.3).
2. **`attempts` в `marking_sell_queue`** теперь = число claim'ов (обработок), а не число
   сбоев; инкремент в claim. Роумоды: `attempts >= 3` — строка больше не снимается.
3. **Двойная обработка `/cis/sell` исключена на уровне кода** — даже если ЛМ ЧЗ не знает
   об идемпотентности: КИ из `/cis/sold` не отправляются повторно.
4. **`APP_ENV` обязателен и обязан быть из whitelist** во всех контурах, где идёт чек с КМ
   (включая mock-обёртку): dev|test|prod|production. `staging` и прочие значения —
   `RuntimeException` до отправки чека.
5. **HTTP 203 от CDN теперь активирует `marking_emergency_state`** (последующие проверки —
   allowAll по ИНН без обращений к ГИС МТ, до `confirmEnd`).

## 7. Ограничения и примечания

1. **Кап выгрузки `/cis/sold` — 5000 КИ** (пагинация по 100): если КИ строки за пределами
   первых 5000 проданных, они отправятся повторно; ЛМ ЧЗ должен отклонить как дубль
   (не критично — задокументировано в `SellWorker::soldIntersection`).
2. **Lease 15 минут** зашит константой `LEASE_MINUTES` (не конфиг): при экстремально
   долгих батчах воркер обязан успеть вызвать `extendLease()` (вызывается перед каждым
   HTTP-вызовом — на практике батч ≤ 100 КИ при `read_timeout` 10 с не приближается к 15 мин).
3. **203 с невалидным телом** → `allowAll` (аварийное разрешение) — источник «аварийный
   режим ГИС МТ»; лог `hybrid_online_203` + метрика пишутся в любом случае.
4. **Mock-интеграция** не покрывает lease/backoff напрямую (детерминированные гонки на
   однопроцессном CLI-сервере ограничены) — эти ветки покрыты unit-тестами
   (`WorkerStaleReclaimTest`, `SellWorkerTest`).
5. Внешние блокеры (JSON Атола — Q3, живой ЛМ ЧЗ, sandbox-токен — Q4a, регионы — Q2a,
   письменное утверждение SPEC) — без изменений; Q8 закрыт (BLOCK), Q9 — MVP-решение
   (SPEC §2.4.1).
