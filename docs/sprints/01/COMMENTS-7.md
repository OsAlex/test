## Проблема 1. `/cdn/info` «выдаёт токен» — фактическая ошибка

**Что сломано:**
- План, Блок 6, Q7: «сначала получить токен через `GET /cdn/info`»
- Открытые_вопросы, Q7: тот же текст
- SPEC §3.2: «`GisMtAuthService::ensureToken()` → получить X-API-KEY» без указания откуда

**Root cause:** `/cdn/info` возвращает **список CDN-хостов**, не токен. И сам требует `X-API-KEY`. Токен выдаёт `/api/v3/true-api/auth/permissive-access` (или берётся из `.env`).

**Fix (патч текста):**

В SPEC §3.2 заменить:
```
1. GisMtAuthService::ensureToken() → получить X-API-KEY.
```
на:
```
1. GisMtAuthService::ensureToken() → прочитать из config('marking.api_key'),
   проверить expires_at; если истёк — POST /api/v3/true-api/auth/permissive-access.
```

В Плане, Блок 6, Q7 — заменить «через `GET /cdn/info`» на «из `.env`/`config`, при истечении — `/auth/permissive-access`».

**Как проверить:**
- Открыть методичку v17, §1.4 — там указано, что `/cdn/info` требует `X-API-KEY` и возвращает `hosts[]`.
- Проверить на sandbox: `curl -H "X-API-KEY: <token>" https://cdn01.crpt.ru/api/v4/true-api/cdn/info` → в ответе нет поля с токеном.

- SPEC §2 (Модели данных) **не содержит** таблицы для их хранения.

CREATE TABLE marking_emergency_state (

**Как проверить:** после добавления — `SHOW CREATE TABLE marking_emergency_state;` соответствует §1.4.

## Проблема 4. `status='skipped'` — семантическое противоречие

**Что сломано:**
- SPEC §2.1: «`skipped` — **запись не создаётся** вообще».
- Но `skipped` входит в `ENUM` столбца `status` таблицы `marking_sell_queue`.

**Root cause:** если запись не создаётся, статус `skipped` никогда не будет записан. Столбец в ENUM избыточен.

**Fix (вариант 1 — убрать из ENUM):**

```sql
status ENUM('pending','processing','done','failed') DEFAULT 'pending'
```

`is_marked=false` → запись не создаётся, `source=SKIPPED` пишется только в `marking_check_history`.

**Fix (вариант 2 — оставить в ENUM, но переопределить):**

```sql
status ENUM('pending','processing','done','failed','skipped') DEFAULT 'pending',
skip_reason ENUM('not_marked','duplicate','cancelled_pre_fiscal') NULL
```

Тогда `skipped` = «запись была создана, но по `skip_reason` не должна регистрироваться». Это осмысленный статус.

**Как проверить:** посчитать, сколько записей в БД имеют `status='skipped'` при текущем определении (если бы БД существовала). Если 0 — статус мёртвый, выбирать вариант 1.

marking_check_total — counter — общее число проверок (знаменатель).

**Как проверить:** `grep -P '[\x{4e00}-\x{9fff}]' SPEC.md` не должен находить ничего. `grep "BV" SPEC.md` — либо определение, либо отсутствие.

## Проблема 10. `packageType=GROUP` в §1.6.1 — неясно, где хранится `parent`

**Что сломано:**
- SPEC §1.6.1 описывает локальный pre-check: «по `cis` агрегата = `parent` единиц».
- Но `parent` в `MarkingCodeResult` от API `/codes/check` — есть. А в офлайн `/cis/outCheck` — **нет** (ЛМ ЧЗ не возвращает `parent`).
- Значит, для офлайн-проверки локальный pre-check агрегатов невозможен по этому полю.

**Fix — в SPEC §1.6.1 добавить явное ограничение:**

```
Pre-check агрегатов выполняется ТОЛЬКО для онлайн-проверки (есть parent в ответе /codes/check).
Для офлайн-ветки (ЛМ ЧЗ) pre-check невозможен — ЛМ ЧЗ не возвращает parent.
Если в чеке одновременно агрегат и единицы, а онлайн-ветка недоступна → запретить продажу
(BLOCK) до восстановления онлайна.
```

**Как проверить:** проверить формат `/cis/outCheck` на sandbox — убедиться, что `parent` не приходит.
