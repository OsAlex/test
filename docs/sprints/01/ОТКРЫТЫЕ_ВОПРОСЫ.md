## Q1. Дата запуска

**Вопрос:** Дата запуска — 01.03.2026 или 01.04.2026?

**Контекст:** В COMMENTS.md §4.5 indicated both options without schedule binding. Affects prioritization and which scenarios (emergency situations, 72h sync) must be covered before release.

- По методичке v17 срок токена продлён до 01.10.2026 — значит, до этой даты вся система уже должна работать.

## Q2. Тайм-зона

**Вопрос:** Все чеки — только MSK, или нужна возможность выбора тайм-зоны из конфига?

**Контекст:** Фаза 1 §2.3.2 зафиксировала `timeZone = 2 (MSK)`. Вопрос о гибкости остается.

**Ответ (COMMENTS-3.md + COMMENTS-4.md):** **MVP — Only MSK**, `timeZone = 2`. Интерфейс `Cassa::getTimeZone()`: возвращает целое число 1..11, по умолчанию `2` (MSK), fallback — `config('marking.default_timezone')`. Переменная `timeZone` влияет на формирование `smp`/`mrp` для групп КМ **3, 12, 16**.

**Обоснование (COMMENTS-4.md):**
- Абсолютное большинство российского retail — MSK/МСК+. Если все кассы в одном регионе — конфиг не нужен.
- **Но:** `timeZone` влияет на возврат `smp`/`mrp` (товарные группы 3, 12, 16). Если хотя бы одна касса в Калининграде (UTC+1) — MSK-значения `mrp` могут не совпасть с реальной минимальной ценой, и проверка цены ниже МРЦ даст ложный результат.
- В ФФД-1.2/Атол `timeZone` — это **часовой пояс МЕСТА РАСЧЁТА**, а не офиса компании.

**Что делать (COMMENTS-4.md):**
1. Получить у заказчика список регионов присутствия.
2. Если все в MSK — зафиксировать `2` в конфиге.
3. Если есть регионы — сделать `Cassa::getTimeZone()` (поле в таблице касс) со значением по умолчанию `2`.
4. В SPEC явно указать: **диапазон 1..11, дефолт 2, при отсутствии значения в кассе — фоллбэк на `config('marking.default_timezone')`**.

**Под-вопросы:**
- Q2a: Список регионов клиента для настройки timeZone — **еще не получен** (прямой запрос нужно).
- Q2b: Default timeZone 2 (MSK) подходит для всех чеков — **подтверждено** для MVP.

**Откуда:** COMMENTS.md §4.7, COMMENTS-3.md Часть 1, COMMENTS-4.md.

**Статус:** **Ответован** (MSK-only для MVP, нужен список регионов для будущего расширения).

## Q3. Официальный JSON-пример Атол (ДККТ 10.10.8.24) — тег 1260

**Вопрос:** Какой официальный JSON-пример тегов `industryInfo.attribute[].attribute[]` (1262–1265) предоставляет Атол?

**Контекст (COMMENTS-2.md §2.1):** План исходно изобрёл семантику тегов, что противоречит PIOT §6.3:
- `1262` = ИД ФОИВ (например `"030"`);
- `1263` = Дата документа основания (формат нужно уточнить: **ISO (YYYY-MM-DD)** или **ДД.ММ.ГГГГ**);
- `1264` = Номер документа основания (источник: **config** или **ГИС МТ**);
- `1265` = аудит-трейл `UUID=...&Time=...&Inst=...&Ver=...` (обязательный; ONLINE без `Inst`, OFFLINE с `Inst` + `Ver`).

**Ответ (COMMENTS-3.md + COMMENTS-4.md):** Структура Атол API v2 (port 16732, `api/v2/requests`): `industryInfo` на уровне `item` в `items[]`, `type: additionalAttribute`, тег **1260** = `additionalAttribute`.

**Ожидаемый JSON-пример (из COMMENTS-4.md):**
```json
{
  "industryInfo": {
    "type": "additionalAttribute",
    "name": "Отраслевой реквизит",
    "value": [
      {
        "id": "1260",
        "value": {
          "1262": "030",
          "1263": "21.11.2023",
          "1264": "1944",
          "1265": "UUID=...&Time=...&Inst=...&Ver=2.0"
        }
      }
    ]
  }
}
```

**Важные замечания (по COMMENTS-4.md и PIOT §6.3):**
- **Тег 1262 = "030"** — ИД ФОИВ. Для маркировки это код **ФНС**. Уточнить у Атоль: не должен ли быть `"030"` или другой код (по опыту, 030 — ФНС, но для разных товарных групп могут быть разные ФОИВ — например, Росалкогольрегулирование).
- **Тег 1263 = дата документа** — **ДД.ММ.ГГГГ** per ФФД, но у Атол может быть ISO. Уточнить.
- **Тег 1264 = номер документа** — для маркировки это обычно номер постановления/приказа. **Откуда берётся?** Нужно зашить в конфиг или получать из ГИС МТ.
- **Тег 1265 = audit trail** — критично. Формат: `UUID=<reqId>&Time=<reqTimestamp>&Inst=<inst>&Ver=<version>`.
  - Онлайн: без `Inst` (по методичке v17, `Inst` — только для офлайна).
  - Офлайн: с `Inst` и `Ver`.

**Если официальный JSON-пример не получен к Шагу 2 — в SPEC оставить плейсхолдер `<INSERT_ATOL_OFFICIAL_EXAMPLE>` + "no invented semantics", без кода (Шаг 3).**

**Под-вопросы (по COMMENTS-4.md):**
- Q3a: **ФОИВ код** — "030" vs others — **уточнить у Атол через ДТО 10.10.8.24**.
- Q3b: **1263 date format** — ISO (YYYY-MM-DD) vs ДД.ММ.ГГГГ — **ДД.ММ.ГГГГ** per ФФД, уточнить у Атоль.
- Q3c: **1264 document-number source** — **config vs ГИС МТ** — уточнить, пока placeholder.

**Откуда:** COMMENTS.md §2.2, COMMENTS-2.md §2.1, COMMENTS-3.md Часть 1, COMMENTS-4.md.

**Статус:** **Ответован** (структура известна, под-вопросы в процессе уточнения).

## Q5. Хранение `X-API-KEY`

**Вопрос:** Где хранится `X-API-KEY`?

**Контекст:** COMMENTS.md §4.6. Ключ не хранится в БД; предполагается `.env` + `config('cz.api_key')`.

**Ответ (COMMENTS-3.md + COMMENTS-4.md):** `.env` + `config('cz.api_key')`. **Никогда не логировать полный ключ** — редигстрировать как `MARKING_API_KEY=sk-…` (обрезанная строка) или `sha1(token)` / первые 8 символов.

**Дополнения (COMMENTS-4.md):**
1. **Не логировать** значение токена ни при каких обстоятельствах (в том числе в `marking_check_history`, в `Logger`, в Sentry). В логах — только `sha1(token)` или первые 8 символов.
2. **Ротация:** ГИС МТ автоматически продлевает токен на стороне Оператора, но в проекте нужно предусмотреть **ручную ротацию** через админку/артизан-команду (если токен скомпрометирован).
3. **Валидация при старте:** при загрузке приложения — проверять `expires_at`. Если токен истёк — не падать, а логировать **critical** и работать в offline-only режиме (если ЛМ ЧЗ готов).
4. **`.env.example`** — обязательно добавить без реального значения:
   ```
   GIS_MT_TOKEN=
   GIS_MT_TOKEN_EXPIRES=2026-10-01
   COMPANY_INN=
   ```

**Под-вопросы:**
- Q5a: Настроена ли ротация токена в текущем проекте — **нет, нужно добавить в Step 2**.

**Откуда:** COMMENTS.md §4.6, COMMENTS-3.md Часть 1, COMMENTS-4.md.

**Статус:** **Ответован** (.env + config, never log key (sha1/first 8), 401 ≠ CDN down, ротация, .env.example).

## Q7. `X-API-KEY` на `/cdn/health/check` (новый, COMMENTS-2.md §2.4)

**Вопрос:** Автентифицирован ли endpoint `GET /cdn/health/check`? Если да — в каком порядке вызывается health-check относительно получения токена?

**Контекст (COMMENTS-2.md §2.4 + методические §8 + COMMENTS-4.md):** Методические рекомендации требуют `X-API-KEY` на `GET /cdn/health/check`. Но в текущем дизайне `CdnService` выполняет health-check **до** получения токена (чтобы проверить доступность CDN перед тем, как запрашивать auth). Если endpoint автентифицированный, health-check на старте вернёт 401 → **ложный срабатывание circuit breaker** (CDN считается мёртвым до первого успешного `permissive-access`).

**Ответ (COMMENTS-4.md — окончательный): Вариант A — health-check вызывается ПОСЛЕ получения токена.**

**Обоснование (COMMENTS-4.md):**
- Все endpoint'ы CDN API ГИС МТ (`/cdn/info`, `/cdn/health/check`, `/codes/check`) требуют `X-API-KEY` (методичка v17, раздел 1.4).
- Токен получается **не через CDN**, а через отдельный endpoint `/api/v3/true-api/auth/permissive-access` (или из ЛК ЧЗ вручную).
- `/auth/permissive-access` **не требует CDN** — это прямой вызов к ГИС МТ. Поэтому циклической зависимости нет.

**Правильный порядок вызовов (из COMMENTS-4.md):**
```
1. GisMtAuthService::ensureToken()
   → POST /api/v3/true-api/auth/permissive-access (или из .env)
   → получить X-API-KEY, expires_at

2. CdnService::getPlatforms()
   → GET /cdn/info (с X-API-KEY)
   → список хостов

3. CdnService::selectBest()
   → GET /cdn/health/check на каждый хост (с X-API-KEY), таймаут 2с
   → выбрать минимальный avgTimeMs

4. CodeCheckService::check()
   → POST /codes/check на выбранный хост (с X-API-KEY)
```

**Что добавить в план (критично, из COMMENTS-4.md):**
- **Отдельный случай: 401 на health-check.** Это **не** «CDN down», а «токен истёк». Должен быть **отдельный код ошибки** и **отдельная реакция** — обновить токен и повторить, а не помечать CDN как нерабочий.
- **Тестовый сценарий:** «просроченный токен → health-check 401 → рефреш токена → повтор health-check → успех».
- **Метрика:** количество 401 на health-check. Если > 0 — алерт (токен не обновляется).

**Вариант B (unauthenticated health endpoint)** — уточнить у Оператора ЧЗ. В методичке v17 явного такого endpoint нет. **Вариант C — избыточен** и создаёт путаницу.

**Откуда:** COMMENTS-2.md §2.4, методические рекомендации §8, COMMENTS-4.md.

**Статус:** **Ответован** (вариант A: token first, then health-check; 401 ≠ CDN down; детальный порядок вызовов).

## Q9. Кто заполняет `cod_marking_*` / `is_marked` в `cassa_ord_det`? (новый, COMMENTS-9 Fix #12; SPEC §2.4)
