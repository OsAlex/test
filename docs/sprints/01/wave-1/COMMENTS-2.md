## Фаза 4. Защита от повтора

**Цель:** чтобы следующая находка не превратилась в волну 2.5.

### 4.1. Правило «нет отчёта без диагностики»

В `docs/sprints/01/STATUS.md` — явно:

> Любой фикс должен включать: (а) вывод `php tests/run_all.php` до, (б) вывод после, (в) какие тесты упали при попытке, если упали. Отчёт без этих трёх вещей — не отчёт.

### 4.2. Правило «не удалять retry при падении тестов»

При падении тестов после изменения retry-логики:
1. Остановиться.
2. Записать failing log.
3. Идентифицировать причину.
4. Исправить причину.

**Нельзя** «откатить, потому что ломает тесты» без записи причины.

### 4.3. Rule of three

Если после 3 последовательных фиксов одна и та же функциональность не закрывается — остановиться, написать диагноз, не начинать четвёртый фикс.

**Критерий фазы 4:** правило зафиксировано в STATUS.md, доступно команде.

## Последовательность (без сроков)

```
Фаза 0 (признание)         ── 1 абзац в STATUS.md
    ↓
Фаза 1 (диагностика)       ── 4 вывода команд, DIAGNOSIS.md
    ↓ [gate: причина падения известна]
Фаза 2 (фикс 2.6)          ── 1–3 коммита, тесты зелёные
    ↓ [gate: Q10-тест зелёный]
Фаза 3 (документы)         ── 1 коммит, отчёты без противоречий
    ↓
Фаза 4 (защита)            ── правила в STATUS.md
```

**Каждый gate — жёсткий.** Без прохождения gate нельзя переходить к следующей фазе. Это и есть отличие от волнового цикла.

- **Не трогаем emergency/cron/throttle.** Это отдельные темы. Здесь — только 2.6.
- **Не запускаем mock-интеграцию.** Она не про retry. Отдельно.
